## 單純的 Prompt 是單次指令，而 **Loop（循環）則是一個給定目標的自主系統** 。
- **驗證器**（Validator）
- 一個能客觀判斷真假的檢查機制（如測試、指標、Benchmark） 。如果沒有它，Agent 只會陷入「自我認同」的幻覺中 。
- **狀態文件**（State File）
- 記錄過去嘗試過什麼、失敗了什麼，避免 Agent 在每一輪循環中重複犯錯 。
- **停止條件（Stopping Condition）**
- 明確定義何時收工（如目標達成，或達到最大嘗試輪數 $N$

##### 第一層：Karpathy 的「單層循環」 (AutoResearch)
Agent 讀取代碼 $\rightarrow$ 提出修改 $\rightarrow$ 訓練固定時間 $\rightarrow$ 驗證指標是否變好 ：
- **變好：** Commit 提交，成為新的基線（Baseline） 。
- **沒變好：** Git Reset 回退，重新再來 。
##### 第二層：Bilevel Autoresearch（雙層自動研究）
| **雙層結構**                 | **負責對象**        | **運作邏輯**                                                          |
| ------------------------ | --------------- | ----------------------------------------------------------------- |
| **內層 Loop (Inner Loop)** | **優化模型**        | 負責具體的寫代碼、訓練、評估、回退或保留（即 Karpathy 原本那套） 。                           |
| **外層 Loop (Outer Loop)** | **優化「內層的搜索策略」** | 不碰模型，只「盯著」內層的運行軌跡。分析內層卡在哪裡，然後**生成新的 Python 代碼去改變內層「怎麼搜」**，注入給內層 。 |
**核心啟示：** 兩層使用的是**同一個 LLM** 。這種巨大的飛躍**來自「架構（Architecture）」的升級，而非來自「更聰明的模型（Intelligence）」** 。

適不適合搭成 Loop，最致命的篩選條件是：**「驗證能不能自動化？」**

- 適合的場景：**能自動判真假的裁判** 。
- 不適合的場景：**對錯只能靠人判斷** 。
