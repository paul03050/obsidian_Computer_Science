這份文件主要是在教你：**當客戶向網路中文購買 SSL 憑證後，下載並解壓縮憑證壓縮檔，裡面各種檔案分別是什麼，以及應該在什麼情況下使用。**

對客服而言，最重要的是分辨以下四種東西：

1. 網站憑證（Server Certificate）
    
2. 根憑證（Root Certificate）
    
3. 中繼憑證（Intermediate Certificate）
    
4. CA Bundle（憑證鏈整合檔）
    

我用實際客服處理情境來說明。

# **一、先理解 SSL 憑證的組成**

**SSL 憑證信任鏈（Certificate Chain）**

第一層

**網站憑證（Server Certificate）**

證明這個網站的網域身分

例如：www.example.com

第二層

**中繼憑證（Intermediate Certificate）**

負責建立網站憑證與上層 CA 的信任關係

第三層

**根憑證（Root Certificate）**

信任鏈的最上層，通常預先存在作業系統或瀏覽器的信任庫

可以把它想成：

- 網站憑證：網站的身分證。
    
- 中繼憑證：負責證明網站憑證是由受信任的 CA 體系簽發。
    
- 根憑證：最上層的信任來源。
    

注意：實際驗證鏈可能不只一張中繼憑證，也不一定需要伺服器傳送根憑證。

# **二、CER - CRT Files 資料夾**

這個資料夾主要放置副檔名為 `.crt` 的憑證檔案。

以 Sectigo（原 COMODO）為例：

|檔案名稱|功能|
|---|---|
|`xxx_xxx_xx.crt`|網站憑證|
|`AAA Certificate Service.crt`|舊版 AddTrust 根憑證相關檔案|
|`USERTrustRSAAddTrust.crt`|USERTrust RSA 相關交叉簽署憑證|
|`SectigoRSA...CA.crt`|Sectigo 中繼憑證|
|`My_CA_Bundle.ca-bundle`|整合多張 CA 憑證的信任鏈檔案|

這裡有一個技術細節值得注意：

文件列出的 AddTrust、USERTrust 等名稱，屬於特定時期 Sectigo 憑證鏈的配置。現在實際使用的憑證鏈可能不同，不能單憑檔名就認定每一張都是目前必要的憑證。

**客服實務：**

如果客戶詢問：

「我下載 SSL 憑證後，為什麼有這麼多個 CRT 檔案？」

可以回答：

這些檔案分別代表網站憑證及 CA 信任鏈中的憑證，依照您的伺服器環境，可能需要安裝網站憑證與對應的中繼憑證，確保瀏覽器能正確驗證網站的憑證來源。

# **三、My_CA_Bundle.ca-bundle 是什麼？**

客服常見重點

這個檔案非常值得熟悉。

CA Bundle 可以理解為：

**將多張 CA 憑證按照信任鏈所需順序整合在同一個檔案中。**

例如：

```
-----BEGIN CERTIFICATE-----
中繼憑證 A
-----END CERTIFICATE-----

-----BEGIN CERTIFICATE-----
中繼憑證 B
-----END CERTIFICATE-----

-----BEGIN CERTIFICATE-----
其他必要 CA 憑證
-----END CERTIFICATE-----
```

實際內容依照 CA 提供的憑證鏈而定。

為什麼需要它？

假設客戶只安裝網站憑證，卻沒有正確安裝必要的中繼憑證，就可能發生：

- 瀏覽器無法建立完整憑證鏈。
    
- SSL 檢測工具顯示 Chain 不完整。
    
- 部分裝置或瀏覽器出現憑證信任錯誤。
    

因此，某些伺服器環境會要求客戶另外提供 CA Bundle。

**但不是所有伺服器都使用同一種安裝方式。**

例如 Apache、Nginx、Plesk、IIS 的操作方式可能不同。

# **四、PKCS7 File 是什麼？**

PKCS#7 是一種憑證封裝格式。

常見副檔名：

- `.p7b`
    
- `.p7c`
    

它可以包含：

- 網站憑證
    
- 中繼憑證
    
- 其他相關憑證
    

通常不包含私密金鑰（Private Key）。

常見使用情境：

|環境|可能用途|
|---|---|
|Microsoft IIS|匯入憑證|
|Windows|憑證匯入及管理|
|Java Tomcat|憑證格式轉換或相關部署流程|
|Azure|依服務支援的憑證格式匯入|

這裡要特別區分：

PKCS#7 不等於 Private Key。

如果客戶只有 `.p7b`，通常不能直接把它當成包含私鑰的完整憑證備份。

# **五、Plain Text Files 是什麼？**

這個資料夾主要是將憑證內容以純文字形式提供。

例如：

```
-----BEGIN CERTIFICATE-----
MIID...
憑證內容
...
-----END CERTIFICATE-----
```

它與 `.crt` 的主要差異在於檔案呈現及副檔名，而不是憑證本身的密碼學功能。

如果客戶需要 `.crt` 格式，可以透過另存新檔方式儲存，但必須注意：

- 保留完整憑證內容。
    
- 保留 BEGIN CERTIFICATE 與 END CERTIFICATE 標記。
    
- 確認副檔名正確。
    
- 不要把多張憑證內容錯誤混在一起。
    

# **六、!PRIVATE KEY INFO!.txt 是什麼？**

這份文件非常重要，因為它提醒客戶：

**SSL 憑證檔案通常不會包含私密金鑰。**

先理解 CSR 與 Private Key 的關係：

**SSL 憑證申請流程**

1. **客戶產生 Private Key**
    
    私密金鑰保存在客戶端。
    
2. **產生 CSR**
    
    CSR 包含公鑰及申請憑證所需的資訊。
    
3. **提交 CSR 給 CA**
    
    例如 Sectigo，進行網域或組織驗證。
    
4. **CA 簽發 SSL 憑證**
    
    CA 根據 CSR 中的公鑰簽發網站憑證。
    
5. **客戶安裝憑證**
    
    使用網站憑證搭配原本產生的 Private Key。
    

這裡有個重要觀念：

CSR 是由 Private Key 推導出公鑰後產生的申請檔案，但 CSR 本身不包含 Private Key。

因此，如果客戶遺失 Private Key：

- 單純重新下載 CRT 通常無法解決。
    
- 需要重新產生 Private Key。
    
- 重新產生 CSR。
    
- 視 CA 及產品流程申請重新簽發（Reissue）。
    

客服不能直接把 CRT 當成私鑰提供給客戶。

# **七、Choosing the Right Files to Install.txt**

這個檔案相當於憑證安裝說明書。

它主要告訴客戶：

- 各資料夾放了哪些檔案。
    
- 哪些檔案是網站憑證。
    
- 哪些檔案是中繼憑證。
    
- 哪些格式適合特定伺服器。
    

不過，真正安裝時仍要依照客戶使用的伺服器環境判斷。

# **八、客服實務：客戶詢問時怎麼判斷？**

這部分我建議你直接整理成工作檢查表。

|客戶問題|你要先確認什麼|
|---|---|
|不知道要安裝哪個 CRT|確認伺服器種類|
|客戶說缺少 CA Bundle|確認伺服器是否需要完整鏈檔案|
|IIS 要安裝哪個檔案|確認是否使用 PKCS#7 或 PFX 等支援格式|
|Plesk 要安裝哪個檔案|確認網站憑證、私鑰及 CA 憑證欄位|
|找不到 Private Key|詢問當初 CSR 是在哪台主機產生|
|SSL 安裝後仍然錯誤|檢查憑證鏈、網域、有效期限及伺服器設定|

## **九、實際案例：客戶說「我已經安裝 CRT，為什麼還是 SSL 錯誤？」**

你可以按照以下順序排查：

**SSL 安裝問題排查流程**

1. **確認網站憑證**
    
    網域是否正確？憑證是否過期？
    
2. **確認 Private Key**
    
    是否與憑證中的公鑰配對？
    
3. **確認 Intermediate Certificate**
    
    是否安裝正確的中繼憑證？
    
4. **確認 CA Bundle**
    
    是否需要另外匯入完整信任鏈？
    
5. **使用 SSL Checker 檢測**
    
    檢查憑證鏈、伺服器回傳的憑證及有效期限。
    

## **十、你應該記住的核心觀念**

|名稱|你可以怎麼記|
|---|---|
|CRT|網站憑證或 CA 憑證的常見檔案格式|
|Root|根憑證|
|Intermediate|中繼憑證|
|CA Bundle|多張 CA 憑證整合的信任鏈檔案|
|PKCS#7|憑證封裝格式，通常不含私鑰|
|Private Key|私密金鑰，必須妥善保管|
|CSR|向 CA 申請 SSL 憑證的請求檔|
|PFX / P12|可包含網站憑證與私密金鑰的封裝格式|

**我認為你在網路中文客服工作中，最值得優先掌握的是三個區別：**

1. CRT 與 CA Bundle：前者可能是一張憑證，後者通常整合多張 CA 憑證。
    
2. CRT 與 Private Key：憑證不能取代私密金鑰。
    
3. PKCS#7 與 PFX：兩者都能封裝憑證，但 PFX 可以包含私密金鑰，PKCS#7 通常不包含。
    

只要這三組概念清楚，客戶詢問「下載後有很多檔案，到底要安裝哪一個」時，你就比較不容易混淆。

你貼的這段是網路中文憑證壓縮檔的官方說明。客戶說「上游 CA 給的 CRT 和客服寄的不一樣」，對照這段說明，**最可能的原因就是「檔案組成方式不同」**——CA 後台讓客戶個別下載，而網路中文寄送的是已經整理好的整套壓縮檔。

### 用這段說明回應客戶的具體方向

**1. 客戶拿到的可能是「單一網站憑證」，而網路中文寄的是「整套信任鏈」**
根據說明，`CER - CRT Files` 資料夾裡除了網站憑證（`xxx_xxx_xx.crt`），還包含根憑證、互簽憑證、中繼憑證，以及三合一的 `My_CA_Bundle.ca-bundle`。客戶從 CA 後台可能只下載了「網站憑證」那一個檔案，自然會覺得跟客服寄的「一整包」不一樣。你可以告訴客戶：**我們寄的是完整信任鏈，CA 後台可以個別下載，但安裝時通常需要中繼憑證才能建立完整鏈。**

**2. 客戶比對的可能是不同資料夾裡的同名檔案**
說明提到 `Plain Text Files` 是 `CER - CRT Files` 的純文字版本，「可以利用另存新檔方式儲存成 .crt 格式」。如果客戶拿純文字檔和 `.crt` 檔比對，內容主體相同但呈現方式不同，也會覺得「不一樣」。

**3. 非 Sectigo 品牌的檔案命名不同**
說明也提醒，非 Sectigo 品牌「未必會有附上中繼憑證及根憑證」，要靠 `Root`、`Intermediate` 等關鍵字辨認。如果客戶用的是別家 CA，檔名和資料夾結構本來就不同，不能直接跟網路中文的 Sectigo 範例比對。

### 給客服的實務話術

> 「您從 CA 後台下載的通常是單一網站憑證，而我們寄給您的是整理好的完整壓縮檔，裡面包含網站憑證、中繼憑證、根憑證，還有三合一的 `My_CA_Bundle.ca-bundle`。這是因為安裝時通常需要完整信任鏈，不是只有網站憑證就夠。您可以打開 `CER - CRT Files` 資料夾，對照 `Choosing the Right Files to Install.txt` 的說明，確認每個檔案的用途。如果您還是不確定該用哪個，告訴我您的伺服器類型（Apache/Nginx/IIS），我幫您確認該放哪幾個檔案。」

### 一個要提醒客戶的點

說明裡有 `!PRIVATE KEY INFO !.txt`，明確寫著「憑證檔不含私密金鑰」。如果客戶比對時發現「少了私密金鑰」，這是正常的——私密金鑰是客戶自己產生 CSR 時留下的，CA 和網路中文都不會提供。這一點可以順帶說明，避免客戶誤以為檔案不完整。
